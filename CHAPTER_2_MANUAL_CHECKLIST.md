## D. Items requiring parish or adviser confirmation (not resolvable from code)

11. **Baptism Regular schedule example.** System Rules ¶128 illustrates the Regular schedule with "such as the 1st and 3rd Saturday of the month for baptism." This is parish-configurable data (`service_schedules` table), not hardcoded — confirm with the secretary whether this is still the actual configured schedule, or soften the sentence to a generic example.
12. **Report-period UI wording.** System Rules ¶138–139 state the secretary/cashier generate "weekly, monthly, and yearly" reports. The code (`secretary/reports.php`, `treasurer/reports.php`) builds reports from a free `fromDate`/`toDate` range with a computed period label, not confirmed literal preset buttons. Confirm the actual UI (a screenshot would settle this) before finalizing the wording either way.
13. **Table 35 — Cost-Benefit Analysis figures.** The ₱700/year domain cost and ₱400/month ("₱4,800/year") Render hosting cost are real-world billing figures that cannot be verified from the repository. Confirm against the actual domain registrar invoice and Render billing dashboard.
14. **Render hosting plan/tier.** Technical Requirements claims Docker + Render hosting (confirmed: a `Dockerfile` exists) but no specific plan/tier is stored in the repository (Render plan is configured in Render's own dashboard). Confirm the specific plan name if the manuscript is to name one.
15. **`staff/` folder framing.** Confirm with the development team whether the "Staff & Priest Portal" should be presented in the thesis as literally a second, separate login system (as the code structures it) or described as one logical system with two entry points — this is an editorial/presentation choice, not a correctness issue.
16. **Confirmation and First Communion booking exclusion.** System Rules ¶129 claims these two services are "not booked directly by parishioners" and are secretary-set only. The scheduling engine's First Communion branch falls through to a generic case rather than an explicit secretary-only rule, and this was not conclusively traced to a hard UI block in `parishioner/services.php`/`book.php`. Confirm directly with the live booking page before treating this claim as settled.
17. **Mass intention fee formula.** System Rules ¶131 describes the PSS/fee computation. The dedicated module (`includes/service-fees.php`) exists and is architecturally consistent with the claim, but the exact arithmetic was not traced line-by-line. Recommended if the adviser wants full certainty: a dedicated line-by-line check of that formula against the fee computation described in the text.
18. **Self-cancel-before-confirmed rule (¶135).** Not independently re-traced against the "My Appointments" page in this pass (it is architecturally consistent with Process 11's pseudocode, which was separately confirmed unchanged and accurate). Low risk, but not line-verified.
19. **CSRF coverage ("every form submission").** The CSRF helper (`csrfToken()`/`verifyCsrf()`) is real and was confirmed in the pages sampled, but its presence on *every* form in the system was not exhaustively checked. If the adviser wants to keep the word "every," a full sweep of all form-bearing pages is recommended; otherwise consider softening to "state-changing form submissions."
20. **Requirements table vs. free-text column (Table 9).** A migration comment states that for some services the free-text `services.requirements` column — not the normalized `requirements` table documented in Table 9 — is what the booking page actually renders. Confirm with the live booking-page code which source is authoritative for each service before treating Table 9 as fully accurate.
