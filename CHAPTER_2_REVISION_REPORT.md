## 1. Executive Summary

The manuscript's **System Rules, Event List, Process Specification, and Database Design** sections describe an earlier, materially smaller version of ParishHub. The live system has grown substantially past that description through roughly 50 incremental migrations. The most consequential findings:

1. **The Mass-intention-donation question is resolved.** The draft's own bracketed uncertainty — *"a voluntary offering greater than ₱0.00 (need pag data or 0 jud?)"* — is settled by the code: `parishioner/book.php` line 292 strictly rejects `offeringAmount <= 0` (and caps it at ₱1,000,000). The rule is **"greater than ₱0.00,"** exactly as Test Case 9 already states. The parenthetical note should simply be deleted.
2. **An entire certificate-issuance module is missing from the manuscript.** A fully built system — automatic certificate generation when a Baptism/Confirmation/Wedding/Funeral is completed, plus a separate paid "Certificate Request" re-issuance flow, a dedicated `issued_certificates` table with civil-registry fields (book/page/line number), and generator/workflow/preview code — has **zero mention** anywhere in Chapter 2 (System Narrative, System Rules, Event List, Process Specification, or Database Design), despite "parish certificates" being an explicit audit target. This is the single largest gap found.
3. **The cashier role is coded as "Treasurer," not "Cashier."** `STAFF_ROLES`, the `roles` table, the folder name (`treasurer/`), and `redirectForRole()` all use "Treasurer." The manuscript uses "the cashier" consistently and exclusively. This is a terminology mismatch that runs through System Rules, the Event List, the Process Specification, Database Design Table 1, and the Interface Design object list.
4. **Funeral/Wake scheduling as described no longer exists.** There is no nine-day mourning wait and no fixed 1:00 PM Mass time (`includes/scheduling.php` comments explicitly: *"No waiting period and no fixed time... 30-minute steps"*). The two named options ("Misa sa Lubong," "Misa sa Haya ug Misa sa Sementeryo") have been replaced by three separate bookable services: **Funeral**, **Wake Mass**, and **Special Mass Request**.
5. **Automatic appointment cancellation is the opposite of what's documented.** System Rules ¶135 and Process Specification #30 both state unpaid approved appointments are "automatically cancelled" past their date. The live code's own comment reads: *"approved appointments are NEVER auto-cancelled... Both the Secretary and applicant are notified that rescheduling is needed."* The booking, priest reservation, and documents are preserved, not cancelled.
6. **Significant authentication/security hardening is undocumented**: mandatory email verification before first login, a 5-attempts-per-email/20-per-IP/15-minute login lockout, an administrator-forced "must change password" flow, and a full OTP-based self-service password reset. None of this appears in System Rules ¶140 or the Login Process.
7. **Four database tables documented as separate no longer exist.** `Generated_wedding_forms` + `Generated_baptism_forms` (+ an undocumented `Generated_funeral_forms`) were merged into one `generated_forms` table; `Wedding_booking_drafts` + `Baptism_booking_drafts` were merged into one `appointment_drafts` table. Table 13 (Appointments) is also missing 11 real columns (Pre-Cana, outside-priest, Anointing requester/patient name, preferred burial date/time, payment deadline, requirements-review workflow).
8. **Five real tables have no manuscript entry at all**: `auth_throttle`, `password_reset_otps`, `email_logs`, `app_sessions`, and `issued_certificates`.
9. **Mass intention times are inaccurate.** Sunday is 6:30 AM / 9:00 AM / 4:30 PM, not 6:00/9:00/4:00; Wednesday has its own 5:15 PM-only slot with no 6:00 AM Mass — an exception the manuscript's "Monday to Saturday" wording omits.
10. **Additional real, live services are entirely absent from the service list**: Anointing of the Sick (Hilog) — free, document-free — and the "outside priest" option (naming a visiting priest instead of choosing from the parish roster, available for Baptism, Wedding, and Funeral).
11. **Login is two separate portals**, not one shared form: `auth/login.php` (Parishioner) and `staff/login.php` (Admin/Secretary/Treasurer/Priest), each blocking the other role group.
12. Donation purposes are outdated ("General Donation" does not exist in code; the real list is Church Maintenance, Charity, Mass/Parish Activities, Other/Not Specified, plus an Ongoing-Project option).

Everything else — the request lifecycle (Pending → document review → approve/reject → payment → confirm → complete), PSS fee computation, scheduling-conflict rules (staff day off, blocked dates, Mass-time conflicts, priest availability), guest/reference-code workflow, password hashing, CSRF protection, RBAC, and the bulk of the Interface Design screens — was verified accurate and should be preserved as written.
